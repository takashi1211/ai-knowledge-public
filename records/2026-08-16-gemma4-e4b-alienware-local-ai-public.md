## 目的

Alienware Alpha上でGemma 4 E4Bを実行し、起動可否だけでなく、日本語会話品質、生成速度、CPU/GPU配置、日常利用候補としての実用性を確認する。

## 背景

この環境では、Gemma 3、Qwen、ELYZAなど複数の小型ローカルLLMを検証してきた。今回は、より新しい軽量モデルであるGemma 4 E4Bが、旧型PCでも日常会話に使えるかを確認した。

あわせて、今後のローカルAI活用を、モデル単体の比較から、Open WebUI、Web検索、ローカルファイル読解、Knowledge棚卸し、NAS整理などを含む実用環境へ発展させる方向を整理した。

## 使用環境

- 機器：Alienware Alpha
- CPU：Intel Core i7-4770
- GPU：旧世代NVIDIA GPU、VRAM 2GB
- メモリ：16GB
- OS：Bazzite
- 使用ソフトウェア：Ollama
- モデル：Gemma 4 E4B（`gemma4:e4b`）
- コンテキスト長：4096
- Ollamaのバージョン：記録なし

## 実施内容

### 1. モデルの起動

次のコマンドでモデルを起動した。

```bash
ollama run gemma4:e4b
```

起動後、`ollama ps`で次の状態を確認した。

- Ollama表示サイズ：約9.6GB
- CPU / GPU配置：99% CPU / 1% GPU
- コンテキスト長：4096

### 2. Thinkingを無効化した実行

通常状態では、短い日本語入力でもThinkingへ入る場合があった。日常会話での待ち時間を減らすため、Thinkingを無効化し、速度表示を有効にして実行した。

```bash
ollama run gemma4:e4b --think=false --verbose
```

### 3. 生成速度の測定

| 条件 | eval count | eval rate | prompt eval rate | total duration |
|---|---:|---:|---:|---:|
| 短い説明 | 59 tokens | 約5.70 tok/s | 約13.70 tok/s | 約12.34秒 |
| 長めの回答 | 573 tokens | 約5.47 tok/s | 約67.36 tok/s | 約1分49秒 |

短文と長文の両方で、生成速度はおおむね5.5 tok/s前後だった。

### 4. 生成中のリソース確認

生成中に`top`で次を確認した。

- `llama`プロセス：約365% CPU
- CPU全体：約半分程度を使用
- `llama`プロセスのRES：約10.1GB
- Swap：約2.1GB
- I/O wait：ほぼ0%

CPU全体が常時100%へ張り付く状態ではなかった。

### 5. 日本語会話品質の確認

短い説明、一般的な質問、会話形式のやり取りを試した。確認した範囲では、日本語は自然で、指示への追従も良好だった。

## 結果

- Gemma 4 E4BはAlienware Alpha上で正常に起動した。
- モデルは99% CPU / 1% GPUで配置され、ほぼCPU主体で動作した。
- Thinking無効時の生成速度は約5.47〜5.70 tok/sだった。
- 573 tokensの回答でも、短文時と比べて生成速度が大きく低下しなかった。
- 日本語の自然さと会話の成立性は、利用者の評価では非常に高かった。
- 起動可否だけでなく、旧型PC上の常用チャット候補として検討できる結果だった。

## 失敗・注意点

- Thinkingを有効にした通常状態では、短い日本語入力でも待ち時間が長くなる場合があった。
- CPU全体が100%まで使われなかった原因は確認できていない。
- 速度は同じモデルでも量子化、Ollamaのバージョン、プロンプト、出力長、コンテキスト長、ハードウェア構成によって変わる可能性がある。
- ファイル移動や削除をAIへ任せる構成は未実装であり、将来試す場合も読み取り専用の候補提示から始める必要がある。

## 確認済み

- モデルの起動とOllama上の表示サイズ
- 99% CPU / 1% GPUという配置
- Thinking無効での短文・長文の生成速度
- 生成中のCPU、RES、Swap、I/O waitの観測値
- 試した範囲での日本語会話の成立

## ユーザーの所感

- これまで試したローカルLLMの中でも、Gemma 4 E4Bはかなり高品質と感じた。
- 日本語で普通に会話できた。
- 一般的な会話では、別のPCで試した24B級モデルと同等か、それ以上に感じる場面があった。
- ほぼCPU主体でも安定しているため、GPU利用率を上げること自体より、現在の安定性を重視してよいと判断した。

## 一般論・参考情報

本記録には外部資料による性能評価を追加していない。モデル一般の評価ではなく、この機器と設定で得た実測および利用者の所感を記録している。

## 推測

- VRAMが2GBと小さいことが、モデルがほぼCPU側へ配置された要因の一つである可能性がある。
- CPU全体を使い切らなかった原因として、メモリ帯域などCPU演算以外の部分が先に制約になった可能性がある。
- 高品質な軽量モデルへ検索やローカルファイル参照を組み合わせる方が、モデルを大型化するだけより日常利用価値を高める可能性がある。

## 未検証

- 数日以上の連続利用時の安定性
- 事実精度の体系的な評価
- Open WebUI経由の速度と安定性
- Gemma 4 E4BによるMarkdown、PDF、RAGの品質
- Open WebUIとSearXNG等を組み合わせたWeb検索
- ローカルフォルダとKnowledge Baseの自動同期

## 得られた知見

- 旧型PCでほぼCPU推論となっても、軽量モデルの設計次第では日常会話を検討できる速度と品質になる。
- 日常会話の体感品質は、モデルサイズだけでは判断できない。
- 次の改善段階は、さらに大きいモデルを探すことだけでなく、Open WebUI、Web検索、ローカルファイル、Knowledge、NASを接続する環境整備にある。
- Knowledge棚卸しやNAS整理では、確定的な情報をスクリプトで抽出し、意味判断が必要な候補提示をLLMへ任せる役割分担が有力である。
