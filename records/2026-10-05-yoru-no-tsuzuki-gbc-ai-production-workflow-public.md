# GBC向けAIゲーム制作：素材を先に決め、変換・実装・検証を分担する

ModRetro Chromatic Pluginで短編ADV『夜のつづき』を制作した際の、品質が落ちた工程と改善方法の記録です。結果と測定値は制作者の報告に基づき、記録担当AIによる再検証は行っていません。

## 制作対象と画面設計

作品は、夜の街で再会した人物と、川沿い・公園・自販機のある路地を巡る短編ADVです。直接歩かせる操作ではなく、会話と行き先の選択肢で場面を切り替えます。

当初の立ち絵＋背景＋会話UI方式は、160×144の画面で各要素に割ける情報量が少なく、人物と背景の魅力が落ちました。そこで、ピクセルアート自体を見せる方針へ変更し、人物と背景を一体で設計したイベントCGを重視しました。

夜景は青・紺・紫を土台に、シアン、ピンク、オレンジ、黄色などの光源色を使い、暗さの中で街の光が映える画面を目指しました。

## キャラクター：再描画から最小限の最適化へ

Codex / PluginへGBC向けの絵を直接描かせると、顔・髪・陰影・雰囲気が大きく単純化されました。

改善したのは、良いピクセル元絵を先に作り、`ORIGINAL REFERENCE`として固定する方法です。再解釈・再描画ではなく、元画像をGBC制約へ最小限最適化するよう指示しました。

この方法では、人物を80×100程度で配置し、次の測定結果に収まりました。

- 1タイル最大4色
- UI込み8パレット
- 背景＋人物：最大287 / 384タイル

今回の結果では、品質低下の大きな要因はGBC向けに再描画する工程でした。数値は今回の構成での結果であり、すべてのGBC制作へ同じ上限を適用するものではありません。

## 背景とイベントCG

背景も制約だけを先に与えると、ベタ塗りや記号的な建物になりやすくなりました。まず完成イメージで構図・光源・奥行き・反射・色を決め、その後ピクセル化する方法を試しました。

川沿い・公園・路地のイベントCGは、高精細画像の生成、ピクセル化、GBC向け最適化の順で制作しました。構図・人物位置・ポーズを維持し、各CGは7パレット、1タイル最大4色、約262〜293タイルに収まり、ROM表示を確認しました。

CGは会話枠なしでAを押すまで表示し、本編で見たものだけギャラリーへ解放します。未解放は「？？？」とし、解放状態をセーブして再起動後も維持する仕様を実装しました。

背景も、良いピクセル元絵を固定して最小限最適化する方法が安定しそうだと判断していますが、継続検証が必要です。

## 音楽：先に音楽的骨格を作る

ゼロからBGMを任せると、チャンネルを多く使い、Noiseや細かな音が雑音のように感じられることがありました。

作品には、明確な主旋律があり、会話を邪魔しない恋愛ADV風のBGMが合うと判断しました。直接のMIDI作曲と音声からの自動抽出は、メロディ品質・変換精度が十分ではありませんでした。

比較的良かった流れは次のとおりです。

1. Sunoなど音楽特化AIで元曲を作る。
2. Work / CodexでMIDI化・整理する。
3. Pluginへ音楽的骨格を渡し、GBC向けに編曲する。
4. ROMへ実装し、実際に聴いて確認する。

原曲への忠実さより、GBCで自然に聴こえることを優先しました。この工程の評価は、特定の過去曲を今後も参照曲として使うという意味ではありません。

## 有効だった分業

| 担当 | 役割 |
| --- | --- |
| ChatGPT / 画像生成 | コンセプトと正解となるビジュアル |
| Suno | 元になる音楽 |
| Work / Codex | MIDI化、素材整理、実装判断 |
| Chromatic Plugin | 制約への適合、GB Studio実装、ROMビルド、検証 |

今回の観察では、Pluginはゼロからのアートや作曲より、既存素材の最適化と実装・検証で良い結果を出しました。これは今回の制作における傾向であり、普遍的な能力評価ではありません。

## 動作確認と再利用する考え方

完成ROMをR36SのGBCフォルダへ配置し、ArkOS系のエミュレーション環境で起動・プレイを確認しました。純正Game Boy ColorやChromatic本体での確認とは区別します。

重要な知見は、正解となる素材と方向性を先に決め、AIへ制約内への変換・実装・検証を担当させることです。数値への適合と、画面・聴感の品質を両方確認する必要があります。

Unity / Unreal / Godot等にも応用できそうな分業原則ですが、それらでの有効性は未検証です。
