# Linux上のCodex RemoteとSSHの使い分け、thread競合、安全な試験ツール撤去

## この記録について

Arch LinuxとHyprlandを使用するPCで、SSHとCodex Remoteの役割を切り分け、モバイル端末からLinux実機を操作できる構成を確認した記録である。

あわせて、一部の既存threadで発生したwriter競合、用途に合わなかったYouTube Music系TUI/CLIの評価、安全な撤去方法をまとめる。

認証方法や利用可能なアプリの配布形態は将来変わる可能性があるため、本記録は特定時点の実機検証として扱う。

## SSHとCodex Remoteは別の経路

当初は、別PCのCodex DesktopからSSHでLinuxへ接続すれば、そのLinuxマシンがモバイル版ChatGPTのCodex Remote一覧にも現れると考えていた。

しかし、実際には別の経路だった。

### SSH経由

```text
別PCのCodex Desktop
        ↓ SSH
Linux実機
```

これは別PCからLinuxを操作するためのRemote SSH接続である。

### Codex Remote経由

```text
モバイル版ChatGPT
        ↓ Codex Remote
Linux上のChatGPT Desktop / app-server
        ↓
Linux実機
```

LinuxマシンをCodex Remoteホストとして利用するには、そのLinux側で対応アプリを起動し、Linux自身をRemoteホストとして登録する必要があった。

SSH接続の登録だけでは、Linuxがモバイル側のRemoteホスト一覧へ独立して追加されるわけではなかった。

## Linux側への導入

Linux版アプリはシステム全体へ直接展開せず、ユーザー領域へ配置した。

構成は次のように分けた。

- アプリ本体：ユーザー領域
- 起動用wrapper：ユーザー用実行パス
- desktop entry：ユーザー用アプリケーション領域
- 管理者権限：不要
- 既存のCodex認証情報：変更しない

導入前後で既存の認証ファイルが変更されていないことを確認した。

この状態でLinux上のアプリからRemote登録を行うと、モバイル版ChatGPTのRemote一覧へLinuxマシンが表示された。

## 実機で確認したRemote操作

モバイル端末から新規threadを作成し、Linux実機上で処理を実行できることを確認した。

一方、一部の既存threadは正常に開けなかった。このため、Remote機能全体の成功と、すべての既存threadを再開できることを分けて判断した。

確認できた範囲では、次の運用が実用可能だった。

- LinuxをRemoteホストとして表示する
- モバイル端末から新規threadを作る
- 現在利用中のthreadでLinux実機を操作する
- SSHとCodex Remoteを用途別に併用する

## 古いモデル指定による失敗

一部の新規threadでは、利用終了済みのモデルが指定され、HTTP 400になった。

クライアント更新後、利用可能なモデルを選び直すことで新規threadは正常化した。

Remote接続そのものの障害と、threadに保存されたモデル指定の問題を混同しないことが重要だった。

## active writer競合

既存threadの再開時に、次の種類のエラーが発生した。

```text
thread-store conflict: already has an active writer
```

調査すると、一部のthreadを別のCodex CLIまたはapp-serverプロセスが保持していた。

```text
既存threadを別プロセスが保持
        ↓
Remote側が同じthreadを再開
        ↓
active writer conflict
```

ファイルが空に見える場合でも、実際のwriter ownershipはプロセス側に残っていることがある。

## writer競合時の安全方針

競合が起きた場合、最初からlockファイルやデータベースを削除・編集しない。

次の順序で確認する。

1. 同じthreadを保持しているCLIやapp-serverがないか確認する
2. 実際にwriterを持つプロセスを特定する
3. 不要なプロセスなら通常終了を優先する
4. threadが解放されたことを確認する
5. その後にRemoteから再試行する

保存領域を直接変更するのは、保持プロセスと状態を確認した後の最終手段とする。

## thread一覧が同じ内容に見えた問題

複数のthreadが同じ会話へつながっているように見える事象もあった。

Linux側を確認した範囲では、次は別々だった。

- thread ID
- title
- source
- model
- history mode
- thread history
- parent / child関係
- app-serverのresume先

Linux側で複数threadを同一threadへ強制的にフォールバックしている証拠は確認できなかった。

残った可能性は次のとおり。

- モバイル側の一覧キャッシュ
- UIの選択状態
- 一部既存threadのwriter競合

新規threadによる実用運用が成立していたため、既存threadすべての原因追跡は完成条件に含めなかった。

## SSHとCodex Remoteの使い分け

### SSHが向く用途

- GUIが起動していない状態での復旧
- サービスやログの直接確認
- 別PCからの保守
- ネットワーク経由の通常シェル操作
- Codex Remote自体が起動していない場合の復旧

### Codex Remoteが向く用途

- モバイル端末からLinux実機へ依頼する
- 新規または現在利用中のthreadを継続する
- ChatGPTアプリ内から作業状況を確認する
- Linux側のCodexへ直接タスクを渡す

両者は競合する代替手段ではなく、用途が異なる補完関係として扱う。

## YouTube Music系TUI / CLIの評価

ターミナル上からYouTube Musicを利用するため、複数のTUI / CLI候補を試した。

通常配信曲の検索と再生だけでなく、次が評価上の難所になった。

- Google認証
- ブランドアカウント
- アップロード曲
- 既存ライブラリとの互換性
- 再生バックエンド
- 継続的な保守状況

試したツールは、本人の主要用途を満たさなかった。

一部のツールは技術的に起動・認証できても、実際に必要なライブラリやアップロード曲を扱えなかった。別のツールは保守状態や認証方式に不確実性があった。

「インストールできた」と「目的に適合した」を分けて評価した。

## 導入試験の停止条件

次のいずれかに該当する場合、追加修正を続けず、試験を終了する判断をした。

- 主要な利用目的を満たさない
- 認証方式に無理がある
- 上流の保守状況が不明確
- 既存の安全な利用方法より複雑
- 完成条件から外れた問題調査が拡大している
- 代替手段がすでに存在する

技術的に動かせる可能性があっても、本人の用途に合わなければ導入成功とは扱わなかった。

## 安全な撤去

試験ツールを撤去する際は、対象を先に特定した。

確認した範囲には次が含まれる。

- 実行ファイル
- 設定ディレクトリ
- キャッシュ
- ユーザー用サービス
- 自動起動設定
- 一時的なwrapper
- 試験用ログ
- 実行中プロセス
- 関連して追加した依存物

削除対象を試験ツールに限定し、既存環境が利用している共通ツールは残した。

特に、動画・音声処理など他用途でも利用していた既存ツールは、試験機能の撤去に巻き込まないようにした。

## 撤去後の確認

削除操作だけで完了とせず、次を確認した。

- 対象プロセスが残っていない
- 自動起動設定が残っていない
- 対象の実行ファイルが残っていない
- 不要な設定やキャッシュが残っていない
- 既存のHyprland環境が正常
- SSHとCodex Remoteが引き続き利用可能
- 共通ツールや既存設定を誤って削除していない

試験環境のCleanupも、導入テストの一部として扱った。

## 追加の実用知識

### Hyprlandのwindow rule

設定したwindow ruleが反映されない場合は、想定したアプリ名だけでなく、実際の`class`、`initialClass`、`title`を確認する。

見た目のアプリ名と、Hyprlandが認識しているclassが異なることがある。

### 入力デバイス

追加ボタンの一部は通常のマウスボタンイベントとしてOSへ渡されないことがある。その場合、Hyprlandの標準バインドだけでは扱えない可能性がある。

専用ツールの導入が本当に必要か、目的に対して複雑すぎないかを先に判断する。

## 確認済み・未解決

### 確認済み

- Linux側からCodex Remoteホストとして登録できた
- モバイル端末にLinuxホストが表示された
- 新規threadからLinux実機を操作できた
- SSHとCodex Remoteが別の経路であることを確認した
- 一部の既存threadでactive writer競合を確認した
- 試験したTUI / CLIが主要用途に適さないことを確認した
- 対象を限定した撤去と残骸確認を完了した

### 未解決・未検証

- 一部既存threadを開けなかった全ケースの原因
- モバイル側のthread一覧表示に関する根本原因
- 将来のクライアント更新後も同じ挙動になるか
- 各TUI / CLIの将来バージョンにおける対応状況

## 得られた教訓

1. Remote SSHとCodex Remoteは同じ機能として扱わない。
2. LinuxをRemoteホストにする場合は、Linux自身のRemote登録経路を確認する。
3. Remote全体の成否と、一部既存threadの互換問題を分ける。
4. writer競合時は保存ファイルを直接削除する前に、保持プロセスを確認する。
5. インストール成功と用途適合を分けて判断する。
6. 試験ツールには、導入前から撤去条件と対象範囲を設定する。
7. Cleanup後はプロセス、自動起動、設定、キャッシュ、既存機能を確認する。
8. 未解決問題が完成条件を妨げない場合、記録して作業を完了できる。

## 公開用の処理

- ユーザー名、ホスト名、ローカルIPアドレスを削除した
- SSH鍵、Cookie、認証情報を含めていない
- 個人用の絶対パスを一般化した
- Remoteホストやthreadの固有IDを含めていない
- 投稿時点で変わり得るモデル名や細かなバージョン番号を一般化した
- 特定ツールに対する評価を、検証時点と本人用途に限定した
- 確認済み事項と未解決事項を分離した
