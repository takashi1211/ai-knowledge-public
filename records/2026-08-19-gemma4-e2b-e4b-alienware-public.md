## 目的

Alienware Alpha上でGemma 4 E4BとE2Bを実際に使い、生成速度、CPU/GPU配置、日本語会話品質、文脈理解、固有名詞処理、モデル常駐中のPC全体の余裕を比較する。

## 背景

2026-08-16の検証では、Gemma 4 E4BがほぼCPU主体で約5.5 tok/sを維持し、日本語会話品質も高かった。今回は、より軽いE2Bを追加し、E4Bとの用途分担を検討した。

ローカルLLMの常用性を「起動できるか」「何tok/s出るか」だけで判断せず、モデルをロードしたまま通常のPC作業を続けられるかも評価対象とした。

## 使用環境

- 機器：Alienware Alpha
- CPU：Intel Core i7-4770
- GPU：旧世代NVIDIA GPU、VRAM 2GB
- メモリ：16GB
- OS：Bazzite
- 使用ソフトウェア：Ollama
- モデル：Gemma 4 E4B（`gemma4:e4b`）、Gemma 4 E2B（`gemma4:e2b`）
- その他の条件：Samba、Jellyfin、Open WebUI等と同じPC上で運用
- Ollamaのバージョン：記録なし

## 実施内容

### 1. Thinkingを無効化して実行

モデル起動時にThinkingを無効化し、速度表示を有効にした。

```bash
ollama run gemma4:e4b --think=false --verbose
ollama run gemma4:e2b --think=false --verbose
```

対話開始後は、次のコマンドでThinkingを切り替えられた。

```text
/set nothink
/set think
```

設定系コマンドは次で確認できた。

```text
/? set
```

### 2. 実測値の比較

| 項目 | Gemma 4 E4B | Gemma 4 E2B |
|---|---:|---:|
| Ollama表示サイズ | 約9.6GB | 約7.1GB |
| CPU / GPU配置 | ほぼCPU主体 | 98% CPU / 2% GPU |
| 生成速度 | 約5.5〜5.7 tok/s | 約9.7〜10.1 tok/s |
| コンテキスト長 | 4096 | 4096 |
| 現時点の役割 | 常用チャット候補 | 高速な裏方処理候補 |

E2BはE4Bのおよそ2倍近い生成速度だった。E2Bの最初の短いテストでは、total duration約2.33秒、eval rate 11.26 tok/s、prompt eval rate 17.42 tok/sを確認した。

### 3. 日本語会話と固有名詞の比較

E4Bは、試した範囲で自然な日本語、会話の流れ、指示理解、固有名詞処理がE2Bより安定していた。「神椿スタジオ」を含む翻訳では、最初から`Kamitsubaki Studio`として処理できた。

E2Bでは次の挙動を確認した。

1. 翻訳会話の直後に日常の話題へ移った際、前の翻訳文脈を引きずり、依頼していない英訳を始めた。
2. 「神椿スタジオ」を最初に`Shin-Tsubaki Studio`と誤推測した。
3. 日常相談では、E4Bよりテンプレート的で説明過多に感じる回答が出た。
4. 訂正後は文脈を追い直すことができた。

### 4. モデル常駐中のPC利用を確認

Alienware AlphaではGemma 4をロードした状態でも、待機中のCPU使用率は低く、RAMにも一定の余裕があり、通常のデスクトップ利用を続けられた。

過去に別のWindows 10 / GTX 1060 6GB搭載PCで小型モデルを試した際は、システムメモリの余裕が大きく減り、通常利用との共存が難しい場面があった。この差の原因は今回確認していない。

## 結果

### E4Bの評価

- 約5.5〜5.7 tok/sで安定した。
- 日本語会話、文脈理解、固有名詞処理でE2Bより明確に良かった。
- モデル常駐中もPCの通常利用と共存できた。
- 現時点では常用チャット、日本語文章生成、相談、文脈理解を要する処理の候補とした。

### E2Bの評価

- 約9.7〜10.1 tok/sで、E4Bよりおよそ2倍近く高速だった。
- 日本語そのものは概ね自然だった。
- 文脈の引きずりと固有名詞の誤推測を確認した。
- 常用会話ではE4Bを優先し、分類、定型要約、Knowledge棚卸しの前処理、ファイル整理候補の一次判定などの候補として残した。

## 失敗・注意点

- E2Bは速度が高くても、会話品質がE4Bと同等ではなかった。
- 固有名詞の自然な出力だけで事実性を判断せず、推測による誤りを確認する必要がある。
- E2Bの裏方処理への適性は候補段階であり、実際のKnowledge棚卸しやNAS整理では未検証である。
- 異なるPC間のメモリ余裕の差は観測したが、OS、GPUオフロード、メモリ管理などの原因は切り分けていない。

## 確認済み

- E4BとE2BのOllama表示サイズ
- 記録した条件での生成速度
- E2Bの98% CPU / 2% GPU配置
- Ollama対話中のThinking切り替えコマンド
- E4BとE2Bの会話例で見えた文脈理解と固有名詞処理の差
- Alienware Alphaでモデル待機中のCPU負荷が低く、通常利用を継続できたこと
- 別のWindows環境では、過去の利用時に通常作業との共存が難しかったという実機経験

## ユーザーの所感

- E4Bは、これまで試したローカルAIの中でも日本語会話品質が非常に高かった。
- E2Bは高速だが、常用会話ではE4Bより明確に劣ると感じた。
- E2Bは削除せず、会話品質より速度を優先する裏方処理へ使う価値があると判断した。
- ローカルAIの実用性には、生成速度と回答品質に加えて、モデル常駐中でもPCを普通に使えるかという評価軸が必要だと考えた。

## 一般論・参考情報

本記録には外部ベンチマークや第三者評価を追加していない。モデル一般の優劣ではなく、この機器、設定、会話例で得た実測と所感を記録している。

## 推測

Alienware Alphaと別のWindows環境で通常利用との共存性に差が出た原因候補は次のとおり。ただし、いずれも未検証である。

- WindowsやChromium / Electron系アプリの常駐メモリ消費
- GPUオフロード時のRAM、VRAM、実行バッファの使い方
- LinuxとWindowsのメモリ管理差
- Alienware AlphaではほぼCPU側へ配置され、処理構成が比較的単純になっている可能性
- CPUやメモリ帯域が先に性能上限となり、それ以上の資源を消費しにくい可能性

## 未検証

- E2Bを使った大量分類、定型要約、Knowledge棚卸し、NAS整理候補抽出の精度
- E4Bを数日以上常用した場合の安定性と事実精度
- 両モデルの長時間連続利用時の発熱、消費電力、安定性
- 同一PC・同一OS・同一モデルによるCPU-only、GPUオフロード、CUDA、Vulkanの比較
- WindowsとLinuxの差、GPUオフロード、メモリ管理が通常利用との共存性へ与える影響

## 得られた知見

ローカルLLMの実用性は、少なくとも次の3項目で評価する必要がある。

1. **生成速度**：tok/s、回答完了までの時間
2. **回答品質**：日本語、文脈理解、指示追従、事実性、固有名詞処理
3. **モデル常駐中のPCの余裕**：RAM、CPU、通常アプリとの共存性

今回の環境では、E4Bを会話と判断、E2Bを高速な前処理へ使い分ける方針が最も自然だった。「起動できる」「ベンチマークで速い」だけでは、常用可能かを判断できない。
